# ADR 005 — How the API is shaped

Status: accepted for the prototype (November 2026).

## What I had to decide

The page needs a feed, a single post, and a way to create one. The requirements also talk about drafts, search, favorites and reports. I wanted those buttons in the mockup to do something real, without building the admin side.

## What I picked

JSON over HTTP, under `/api`, except health which is `GET /health` because that's the usual place for "is the process up".

Open routes, so `/docs` can try them with no login:

- `GET /health`
- `GET /api/counter` and `POST /api/counter`
- `POST /api/auth/register` and `POST /api/auth/login`

Routes that need the bearer token:

- `POST /api/auth/logout`, `GET /api/auth/me`
- `GET /api/categories`, `GET /api/tags`
- `GET /api/crafts`, `GET /api/crafts/{id}`
- `POST /api/crafts`, `PUT /api/crafts/{id}`, `DELETE /api/crafts/{id}`
- `POST /api/crafts/{id}/favorite` (it toggles)
- `POST /api/crafts/{id}/reports`, `GET /api/reports`

`GET /api/crafts` takes `q`, `category`, `tag`, `mine`, `status` and `favorites`. The public feed is published posts only. `status=draft` is refused unless `mine=true`, and even then the query is limited to the logged-in user. Asking for someone else's draft by id returns 404, the same as a missing post, so a draft id doesn't confirm that the draft exists.

A published post has to have a title, description, one official category, at least one official tag, dimensions, colors, tools, backstory, and a location. That check is in the server, not only in the form. A draft only needs a title. The photo is a URL and it is optional in this prototype. An empty URL means "show the placeholder".

Updating a post is a PUT that sends the whole post again. The form already has every field, so a partial PATCH would only make the code harder to read. Only the author can update or delete. Anyone logged in can read a published post.

The response for a craft includes `author_name` and `owner`. It does not include the author's email.

## Why

This is the smallest set that makes the mockup's buttons honest. List, read and create were the must. Drafts are a `status` column on the same table, not a second table, because a draft is the same post before it is published. Favorites and reports are there because the heart and the Report button are on the mockup and I didn't want them to be `alert()` calls. `GET /api/reports` only returns the reports the current user sent. There is no admin queue yet, and I don't want to pretend there is.

Categories and tags are a Python list in `constants.py`, not a table. Nothing in the prototype edits them. When an admin screen exists, that list should move into the database. Until then a table with no way to change it is extra ceremony.

## What else I thought about

One endpoint that returns everything and lets the page filter it. Easier client, but then drafts and search rules live in JavaScript where they can be skipped. The server is the place that hides drafts.

GraphQL. Far too much for a dozen routes.

Putting the counter under `/api/debug` or leaving it out of the docs. I want it in `/docs` on purpose. It is the "click this and watch the number" endpoint.

## What I might regret

Official tags that aren't in the database will annoy me the first time someone wants to add "copper". That's a known shortcut. Also, `card_height` is a display hint so the placeholder cards aren't all the same height as the mockup. New posts get 240. It is not a property of the craft, and I might drop it when real photos decide the height.

## Follow-up — drafts stay a status (issue #14)

The prototype already saved a draft as `status = "draft"` on the same `crafts` row. I kept that for the drafts feature. I did not add a column. `create_all` on Render does not change a table that already exists, and the deployed database already has `status`. A new column would stay missing there until the database was dropped. Deleting the Render database is the documented way to change a column, and it was not needed here.

Search, category and tag skip drafts even when the caller also passes `mine=true`. The exception is the draft list itself: `mine=true` and `status=draft`. That list can be narrowed with the same filters, and it is still only the caller's drafts. `mine=true` on its own still returns that user's published posts and drafts. The page splits them: **My posts** asks for `status=published`, **My drafts** asks for `status=draft`.

A draft still only needs a title. Sending `status=published` on create or on PUT runs the full field check first. If the check fails, PUT does not write, so a rejected publish leaves the saved draft as it was. Someone else's draft is a 404 on read, update and delete.
