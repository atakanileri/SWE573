# ADR 007 — Deploy on Render, with Postgres there and SQLite at home

Status: accepted for the MVP deploy (November 2026).

## What I had to decide

The MVP has to be on a public URL, still start from Docker, still show Swagger at `/docs`, and still be something a stranger can deploy from the README. The free Render web service does not keep a disk. SQLite is a file. That file would disappear every time the service redeploys, restarts, or spins down after 15 idle minutes. I needed the sample crafts and the test login to be there when a grader opens the site, and I needed posts created during a demo to still be there after a refresh and a redeploy.

## What I picked

Render, using the Docker runtime, described in `render.yaml` at the repo root.

- One free web service, `indigenous-crafts`, built from the same `Dockerfile` as Docker Compose.
- One free Render Postgres database, `indigenous-crafts-db`, in the same region (Frankfurt). The web service gets `DATABASE_URL` from that database. The password is generated by Render and is not in git.
- The app listens on `PORT` (Render's default is 10000). Locally and in Compose, `PORT` is unset and uvicorn stays on 8000.
- Locally, and in `docker compose`, the database is still SQLite. `database.py` only switches drivers when `DATABASE_URL` is a Postgres URL. I added `psycopg` for that driver and nothing else.
- Tables are still created with `create_all` on startup. I did not add Alembic.
- `SEED_DEMO_DATA`, `DEMO_EMAIL` and `DEMO_PASSWORD` control the sample account. The committed values are the public test login `atakan@example.com` / `password`. Seed runs only when the users table is empty, so a redeploy does not duplicate the crafts or reset that password.

HTTPS is Render's. The container still speaks plain HTTP. `/docs` is the same Swagger page as on my laptop.

## Why

This is the smallest change that makes the deployed data survive a restart.

SQLAlchemy was already taking the database URL from the environment (ADR 002 said Postgres was the thing I would switch to later). The models did not change. The routes did not change, except one cast: tag search used `CAST(... AS VARCHAR)`, and Postgres refuses to cast JSON to `VARCHAR`. It is `TEXT` now, which SQLite also accepts. I can point at that line.

A second container in Compose would have made the local demo harder to explain, for a database I only need on Render. Compose stays one service. The stranger's path is still `docker compose up --build`.

The test password is in the repo on purpose. A grader has to be able to log in without asking me for a secret. The thing that must not be committed is the Postgres password. `fromDatabase` is how Render passes it in without me copying it into a file.

Frankfurt is closer to Istanbul than Oregon, which is Render's default region. The region has to be the same on the web service and the database, or the private database URL does not connect. A free web service is allowed to open that private connection. It cannot receive private traffic itself, which this app does not need.

## What else I thought about

SQLite on the Render disk, and re-seeding whenever the users table is empty. Fewer moving parts, and the test login would come back after every spin-down. Anything a person posted during the demo would vanish the next time the free service slept. That fails the "the counter still has the number after a restart" story, and it fails a grader who publishes a craft and comes back later. I would only accept this if Postgres were unavailable on the free plan. It is available.

A persistent disk on the web service, with the SQLite file on it. Render does not sell that on the free plan.

Neon or Supabase for Postgres. Also a free hosted Postgres, also a `DATABASE_URL`. It is a second account and a second dashboard. The README would be longer, and I would be explaining someone else's control panel. Render's own database is one blueprint.

A paid Render Postgres plan, so the database does not expire in 30 days and so backups exist. That is the right production choice. It is not required for a class MVP, and I did not want the blueprint to create a bill. Both `plan` fields are `free`. Render's default for a new web service is a paid size if you forget `plan`, which is why it is written down.

Putting the demo password only in the Render dashboard (`sync: false`) and not in `render.yaml`. Then a stranger can miss the prompt and the seed falls back to the same default anyway, because that default lives in `seed.py` for the local app and the tests. Writing the public password in the blueprint means the deployed site matches the README without an extra click.

## What I might regret

The free database expires 30 days after I create it. Render then keeps it for 14 more days if I upgrade, and deletes it after that. There are no backups on the free plan. A demo after the expiry needs a new database, and the sample data is re-seeded into an empty one. Posts made in the old database are gone. I will upgrade or recreate it if the demo is still needed.

The free web service sleeps. The first request after 15 idle minutes waits about a minute. I should say that out loud before a live demo, or open the site a minute early.

`create_all` will not alter a table that already exists. The first time I add a column after the database is live, startup will not migrate it. I will drop the Render database (or the local file) and let the seed fill it again. That is acceptable while the data is sample data. It will not be acceptable once real posts matter.

Startup tries to reach Postgres five times, three seconds apart. If Render is slower than that on the first deploy, the deploy fails and I hit redeploy. I would rather have a short, obvious retry than a wait loop I cannot explain.

The image still runs uvicorn as root, with one worker. ADR 006 already says that. Render is in front of it for TLS and for the public port. I did not add a `SECRET_KEY`. Login tokens are random rows in the `sessions` table, not signed cookies, so there is no key for me to invent and then pretend is important.
